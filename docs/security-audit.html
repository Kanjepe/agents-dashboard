Vulnerable pattern

All 16 dynamic UI updates use el.innerHTML = templateString. Template strings DO escape user data via escapeHtml(), but the pattern is fragile - a single forgotten escape in future change becomes a stored-XSS sink.

Evidence

public/app.js:671 
if (filtered.length === 0) {
  listEl.innerHTML = '<div class="activity__empty">// no subagents match this filter</div>';
  return;
}
listEl.innerHTML = filtered.map(renderAgentLibraryItem).join('');
}

function renderAgentLibraryItem(a) {

Impact

Defense-in-depth gap. Current code is safe because every interpolation goes through escapeHtml(). First time someone forgets, payload executes in dashboard context.

Exploit scenario

Hypothetical: someone with write access to ~/.claude/projects/ adds malicious file with session title containing <img src=x onerror='fetch(...)'>. If a future change omits escapeHtml around s.title, payload fires. Today's code is safe.

Fix

Prefer textContent + element.appendChild over innerHTML where possible.

  1. 1. Audit each innerHTML site - static markup is fine.
  2. 2. For dynamic content, refactor to document.createElement + textContent.
  3. 3. As lighter alternative, add unit test that locks in escapeHtml's contract.

  article.className = 'entry';
  const title = document.createElement('h2');

  parent.appendChild(article);
}

HIGH conf: high network informational HTTP server binds to all interfaces by default - LAN exposure server.js:249

Vulnerable pattern

server.listen(PORT, cb) with no host argument binds to :: / 0.0.0.0 by default in Node.js. The dashboard is then reachable from any device on the same LAN. Combined with the design choice of zero authentication (intentional 'localhost only'), anyone on the same network can read the full token-stats history and active Claude Code sessions.

Evidence

server.js:249 
watcher.on('add', onJsonlChange);
watcher.on('change', onJsonlChange);
watcher.on('error', (err) => console.error('[watch] error:', err.message));

server.listen(PORT, () => {
  console.log('\n  Agents Dashboard');
  console.log('  Watching: ' + projectsDir);
  console.log('  Open:     http://localhost:' + PORT + '\n');
});

process.on('SIGINT', () => {
  console.log('\n  Shutting down...');

Impact

A roommate, coworker on shared WiFi, or attacker on a port-forwarded network can open http://<your-ip>:4173 and see every active Claude session, project name, AI-generated session titles (which leak prompt content), and total token usage. JSONL body content is not exposed but inferred metadata is.

Exploit scenario

Attacker on the same LAN scans port 4173, opens the URL in a browser, and reads the live dashboard. No credentials, no challenge. The /api/skill/:slug and /api/agent/:domain/:slug endpoints (now validated) still leak the full body of any skill or agent profile installed on the victim machine.

Fix

Bind the HTTP server explicitly to 127.0.0.1 (or ::1) so only the local machine can connect.

  1. 1. Change server.listen(PORT, () => {...}) to server.listen(PORT, '127.0.0.1', () => {...}).
  2. 2. Optionally expose a HOST env var defaulting to 127.0.0.1 so power users can opt in to LAN access deliberately.
  3. 3. Document the binding choice in README so users understand the threat model.
  4. 4. Verify after fix: from another machine on the LAN, http://<dev-machine-ip>:4173 must time out or refuse the connection.

Safe code

const HOST = process.env.HOST || '127.0.0.1';
server.listen(PORT, HOST, () => {
  console.log('  Open:     http://' + HOST + ':' + PORT + '\n');
});

Verification

  • Get-NetTCPConnection -LocalPort 4173 -State Listen | Select LocalAddress (expected: 127.0.0.1).
  • From a second machine on LAN, curl http://<dev-ip>:4173 must fail.

References

  • https://nodejs.org/api/net.html#serverlistenoptions-callback
  • https://cwe.mitre.org/data/definitions/1327.html
MEDIUM conf: high csrf informational WebSocket endpoint accepts any origin (CSWSH) server.js:170

Vulnerable pattern

WebSocketServer constructed without verifyClient handler or Origin header check. A malicious webpage opened by the user in any browser tab can open a cross-origin WebSocket to ws://localhost:4173/ws and read the same snapshot data the legitimate dashboard receives. The browser does NOT apply same-origin policy to WebSocket connections - only to HTTP fetches.

Evidence

server.js:170 
const server = createServer(app);
const wss = new WebSocketServer({ server, path: '/ws' });

const clients = new Set();

Impact

If the user visits an attacker-controlled webpage while the dashboard server runs locally, the attacker's JS can connect to ws://localhost:4173/ws and stream all session data, token totals, project paths, and registry content out to a remote endpoint. Cross-Site WebSocket Hijacking (CSWSH).

Exploit scenario

Attacker hosts page with: new WebSocket('ws://localhost:4173/ws'). When victim visits, connection succeeds (no origin check). Attacker's JS reads onmessage payloads, JSON.parse them, POSTs full snapshot to a remote server. Victim sees nothing.

Fix

Reject WebSocket upgrades whose Origin header is not http://localhost:* / http://127.0.0.1:*.

  1. 1. Add verifyClient to WebSocketServer options that checks info.origin against an allowlist.
  2. 2. Allow null origin only if you intentionally support file:// or sandboxed contexts.
  3. 3. After fix, attempt WebSocket connection from a different page - it must be rejected with code 403.

Safe code

const ALLOWED_ORIGINS = new Set([
  'http://localhost:' + PORT,
  'http://127.0.0.1:' + PORT,
]);
const wss = new WebSocketServer({
  server, path: '/ws',
  verifyClient: (info, cb) => {
    const origin = info.origin || '';
    cb(ALLOWED_ORIGINS.has(origin), 403, 'forbidden origin');
  },
});

Verification

  • Open a non-localhost page, run new WebSocket('ws://localhost:4173/ws') in DevTools.
  • After fix: connection closes immediately with reason 'forbidden origin'.

References

  • https://cwe.mitre.org/data/definitions/346.html
  • https://christian-schneider.net/papers/CrossSiteWebSocketHijacking.html
MEDIUM conf: high headers informational Missing security headers (CSP, X-Frame-Options, etc.) server.js:141

Vulnerable pattern

Express server uses express.static and JSON endpoints but never sets Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, or Referrer-Policy. No helmet middleware. If an XSS bug were ever introduced, there is no second layer of defense.

Evidence

server.js:141 
const app = express();
app.use(express.static(join(__dirname, 'public')));

app.get('/api/sessions', async (req, res) => {

Impact

Any future XSS regression in the frontend has no CSP backstop. Pages can be iframed by any site (clickjacking). Browsers may MIME-sniff served files.

Exploit scenario

Defense-in-depth gap. If a future contributor adds an unescaped innerHTML write of user-controlled data, an attacker who controls JSONL content can inject script. With CSP set to default-src 'self', inline script would be blocked.

Fix

Add helmet middleware with a conservative CSP suited for a local-only dashboard.

  1. 1. npm install helmet
  2. 2. Add app.use(helmet({...})) before any routes.
  3. 3. Set X-Frame-Options: DENY (no need to be framed).
  4. 4. Test that the dashboard still renders correctly with CSP enabled.

Safe code

import helmet from 'helmet';
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'"],
      styleSrc: ["'self'", "'unsafe-inline'", 'https://fonts.googleapis.com'],
      fontSrc: ["'self'", 'https://fonts.gstatic.com'],
      connectSrc: ["'self'", 'ws://localhost:' + PORT],
    },
  },
}));

Verification

  • Open http://localhost:4173/, check Network tab response headers include Content-Security-Policy.
  • curl -I http://localhost:4173/ expects X-Frame-Options, X-Content-Type-Options.

References

  • https://helmetjs.github.io/
  • https://cwe.mitre.org/data/definitions/693.html
